\bookchapter{The Front End: What Runs on Your Screen}{ch:02-the-front-end}

\begin{chapterintro}

This chapter looks at the side of the app you can see: who draws the screen, the three languages every web page is made of, what a front-end framework adds, and why a phone app is a front end too.

\end{chapterintro}

\emph{The problem.} The same app looks right on my laptop and my phone, but who draws it?

\emph{The question.} How does an app become the picture on my screen, and how does that picture fit every size of screen?

\section{The Server Sends Instructions, Not a Picture}\label{02-the-front-end:the-server-sends-instructions-not-a-picture}

When you open a website, the server does not send a finished picture of the page. It sends \emph{instructions}, and your device draws the page itself.

Think of flat-pack furniture. The shop doesn't deliver a built bookcase. It sends the parts and an instruction sheet, and you assemble it at home. A good sheet even says: ``If your wall is narrow, stack the shelves in one column.''

The program that does the assembling is the \textbf{browser}\index{browser}: Chrome, Safari, Firefox, or Edge. It downloads the instructions, follows them, and draws the result. That is why the same app looks right on a laptop and a phone: each device builds the page to fit its own screen.

\section{One Page, Every Screen}\label{02-the-front-end:one-page-every-screen}

A phone screen is narrow; a laptop screen is wide. Designers don't build two websites. They write CSS rules that change the layout to fit the space: ``on a wide screen, show the menu on the left; on a narrow one, hide it behind a button.'' This is \textbf{responsive design}\index{responsive design}: the ``stack the shelves if the wall is narrow'' line of the instruction sheet.

\section{Front-End Frameworks}\label{02-the-front-end:front-end-frameworks}

The example page has one button. An online shop has thousands, and changing one number can mean five places on the screen must change with it. Doing that by hand in JavaScript is slow and error-prone.

A \textbf{front-end framework}\index{front-end framework} is ready-made code that does this bookkeeping. React, Vue, Angular, and Svelte are well-known ones. The developer describes what the screen should look like for the current data (``the cart shows these three items''), and the framework updates the page whenever the data changes.

Frameworks build screens from \textbf{components}\index{components}: small, reusable pieces such as a product card or a like button. Like building bricks, one component can appear hundreds of times on a page.

\begin{callout}{note}

A framework helps the developer; it is not a new language for the browser. A React app still reaches your browser as HTML, CSS, and JavaScript, the only three languages a browser draws.

\end{callout}

\section{Mobile Apps Are Front Ends Too}\label{02-the-front-end:mobile-apps-are-front-ends-too}

Apps you install from an app store are usually \textbf{native apps}\index{native apps}: programs written for one kind of phone, in languages like Swift (iPhone) or Kotlin (Android). They draw their own screens without a browser.

The tools differ, but the role is the same. A native app shows screens, reacts to taps, and asks a back end for anything it doesn't have. Often one back end serves the website, the iPhone app, and the Android app together.

\section{What the Front End Can't Do}\label{02-the-front-end:what-the-front-end-cant-do}

Everything in the front end travels to the user's device, where the user can read it and change it. So the front end can't keep secrets, and it can't make final decisions. It can say ``this coupon looks valid'', but only the back end can accept it.

\begin{callout}{warning}

Never put a password, a secret key, or a price the customer must not change in front-end code. The back end must check everything the front end sends.

\end{callout}

\section{Try It}\label{02-the-front-end:try-it}

See the instructions behind a real page, and change them.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Open any website on a computer. Right-click a heading and choose \emph{Inspect}. The \emph{Elements} tab shows the page's HTML, with your heading highlighted.
\item
  Double-click the heading's text in that panel, type something new, and press Enter. Then reload the page.
\item
  Click the phone-and-tablet icon at the top of the developer tools (the device toolbar) and pick a phone.
\end{enumerate}

\emph{Expected result:} In step 2 the heading changes to your text, then goes back when you reload. You changed only your own copy of the instructions; the server never knew. In step 3 the page rearranges itself for a narrow screen: responsive design at work.

\section{Summary, Key Terms, and Review Questions}\label{02-the-front-end:summary-key-terms-and-review-questions}

\subsection*{Summary}\label{02-the-front-end:summary}

\begin{itemize}
\tightlist
\item
  The server sends instructions; the browser follows them and draws the page.
\item
  HTML says what is on the page, CSS says how it looks, and JavaScript says what it does.
\item
  Responsive design lets one page fit any screen.
\item
  Front-end frameworks keep large screens up to date, built from reusable components.
\item
  Native apps are front ends too, often sharing one back end with the website.
\item
  The front end can't keep secrets or make final decisions.
\end{itemize}
