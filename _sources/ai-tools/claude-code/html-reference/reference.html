1.1

Background & Context

Case discovery work is currently performed manually through the Lexis legal research platform. Team members execute keyword searches against defendant names, open each matching case, download the complaint document, verify whether the case concerns a data breach, and then enter the case into the firm’s case management system (RCS).

The workflow is repeated campaign by campaign. Each defendant name being tracked requires its own search, and each case returned by that search requires the same sequence of manual verification steps. As described in the walkthrough, going through campaign after campaign and searching each one individually “takes a lot of time.”

The session documented here had two purposes: to record the existing manual workflow step by step so it can be understood by others, and to identify which parts of it could be automated. The conclusion reached was that the majority of cases can be located easily by searching the defendant name, while a smaller number — those with multiple defendants, or those filed in state court — will continue to require manual work.

1.2

Current Workflow

1.2.1Lexis Keyword Search

  1. Open Lexis and go to keyword search.
  2. Enter the search with the required punctuation — an apostrophe and a colon.
  3. Remove the plaintiff party segment, since the name being searched is the defendant.
  4. Run the search.
  5. Change the sort order from relevance to newest to oldest, so the most recent filings appear first.
  6. Review the returned cases — these are the cases carrying the searched name, with the plaintiff shown alongside.

1.2.2Opening and Screening a Case

  1. Open the case from the results list.
  2. Check the complaint detail — the name and the party.
  3. Review the basic information shown on the case record.
  4. Determine whether the case is data breach, privacy, or another category.

1.2.3Retrieving and Verifying the Complaint

Confirming whether a case is a data breach requires opening the complaint document itself; the case record alone is not sufficient.

  1. Go to the document section of the case.
  2. Click on the complaint.
  3. The complaint is shown either as already available or as retrievable online — click the hyperlink.
  4. Select get the document and wait until the download completes.
  5. When the view option appears, open the complaint.
  6. Confirm the case is a class action and check the named party defendant.
  7. Read the basic information and the nature of suit.
  8. Confirm the nature of suit states this is a data breach, and that the complaint refers to personal identifying information and sensitive private information.

1.2.4Entry into RCS

Once a case is confirmed as a data breach, it is inserted into RCS.

1.2.5Repetition Across Campaigns

The full sequence above is repeated for each campaign. The team works through campaign after campaign, searching each individually, which is the primary source of time spent in the current process.

1.3

Core Problem

There is no single place where newly filed data breach cases can be seen. Because discovery is driven campaign by campaign, the same search-and-verify sequence is repeated once per tracked name, and cases are only ever found one search at a time. Locating them individually in this way takes a lot of time.

The verification steps compound the problem: every case returned by a search has to be opened, its complaint downloaded, and its nature of suit read before the case can be classified — and those steps are identical every time.

The team’s assessment

The team’s own assessment is that a majority of cases could be pulled automatically — directly from the defendant name — and that a single daily data breach search would surface all data breach class actions in one place. Only a limited set of cases would still need manual searching.

1.4

Challenges & Limitations

1.4.1Cases That Search Easily vs. Cases That Do Not

Some cases are very easy to search; others are not. The distinction turns on how many defendants the case has and on which court system the case was filed in.

✓Searches easily

  • There is only one defendant.
  • The correct name of the defendant is known.
  • The name can simply be entered, along with data breach, and the case is returned.
  • The result can be reviewed quickly.

!Requires manual work

  • There are multiple defendants.
  • The case was filed in state court.
  • The case has to be searched manually using a different search string.
  • The defendant names themselves are difficult to search.

1.4.2Name Changes Producing Inconsistent Results

A change of name on a matter causes the same case to surface differently depending on where it is looked at. In the example reviewed, four entries were visible in one view — two dated 24 August, one 25 August and one 31 August — while in another view only two options appeared, 24 August and 31 August. The cause was identified as the name change.

1.4.3Volume of Manual Work

The majority of cases can be located easily; only a few rare cases present difficulty. Because that difficult number is small and the straightforward number is large, automating the straightforward cases and handling the remainder manually was judged to make the job easier.

1.5

Goals & Success Criteria

01
Goal 1
A single daily data breach search

Success when one data breach search is conducted every day, rather than searching each campaign separately.

02
Goal 2
All data breach class actions in one place

Success when all data breach class actions fall under a single result set, so all the latest data breach cases filed are available at one place.

03
Goal 3
Cases pulled directly from the defendant name

Success when cases are pulled automatically and directly from the defendant name, without the search being run by hand.

04
Goal 4
No campaign-by-campaign searching

Success when cases no longer have to be searched individually, campaign through campaign.

05
Goal 5
Easier location and insertion into RCS

Success when cases are easy to locate and insert into RCS once they have been surfaced in one place.

06
Goal 6
Manual effort reserved for the difficult cases

Success when manual searching is needed only where there are multiple defendants or the case was filed in state court, and the majority of cases — those locatable by searching the defendant name — are handled automatically.

1.6

Out of Scope

⊘

Cases with multiple defendants and cases filed in state court are not expected to be handled automatically; these will continue to be searched manually using alternative search strings. The discussion did not settle whether any solution exists for automating this category — it was raised as an open question to be put to the team who would build the automation.

1.8

Constraints & Assumptions

Constraints

  • Discovery is performed through Lexis; the search syntax, party segments, sort order and document retrieval steps described above are those the platform requires.
  • Confirming a data breach requires the complaint document itself — the nature of suit and the references to personal identifying information and sensitive private information are found there, not on the case record.
  • Complaint documents must be retrieved before they can be viewed, and the retrieval has to complete before the view option appears.

Assumptions

  • Cases with a single, correctly named defendant can be found by searching that name together with data breach.
  • The number of cases that can be located easily is larger than the number that cannot.
  • A daily data breach search would capture all data breach class actions.
  • Handling the difficult cases manually is acceptable, given how few of them there are.
  • Six worked examples were judged sufficient to convey the process and its edge cases.
