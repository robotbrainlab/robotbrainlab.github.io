Scope

The Python language and the craft around it. One phase steps outside deliberately — building an API is the best vehicle there is for exercising the language under real conditions.

Operating rules

  1. Read specification and instruction in pairsThe official docs are terse and normative; the HOWTOs and books say the same thing in tutorial voice. When a passage doesn’t land, switch registers rather than rereading.
  2. Respect the two real dependencies, and overlap the restOnly two orderings actually matter: 1.1 before 1.3, because 1.3 is a second pass over the same ground, and 1.3 before 1.4, because asyncio needs generators and context managers. Everything else is soft. 1.4 and 1.5 are meant to run together — build the API while you learn concurrency, and put the concurrency into the API. A phase is finished when its phase project is finished, not when you have read every line of it.
  3. Nothing here can tell you how you are doingEvery description of competence on this page is one you grade yourself, and self-assessment is where people overrate themselves. The only reliable correction is another person reading your code. Getting reviewed lists places that will.
  4. Not everything on these lists is the same kind of documentThe Tutorial, the Language Reference and the HOWTOs are prose, written to be read. Most Library Reference pages are not — they are lookup tables, and items below marked “Reference, not a chapter” are flagged so you know which you are holding before you try to read it front to back.
  5. These lists are longer than anyone can hold at oncePhase 1.1 has twenty-three items before its first project, and the start of a list goes cold while you work through the end of it. The projects are proof that a phase landed, not the practice that gets you there. Where that practice comes from is up to you — How to Practise is a set of prompts for generating it.
  6. Build, don’t collectA project you finished teaches more than four you bookmarked.
  7. One thing at a timeDomain tourism — a little scraping, a little data science, a little web — reads as a beginner’s portfolio no matter how many fields it touches. This is an argument against sampling four domains at once, not against having one. Pick a domain deliberately after Stage 1 and go deep into it — that is the whole purpose of getting the language solid first. See What’s Not Here.
  8. Write things downKeep a log of every bug that cost you more than an hour. The second time you hit it you’ll have the answer. Worth more than any book on these lists.
  9. Use whatever is current stableAt the time of writing that is Python 3.14, with 3.15 due October 2026 — you will cross at least one release during this roadmap, which is fine. Always read the /3/ documentation URLs; pinned versions silently serve stale material. Read What’s New when you upgrade.

Priority tags

The standard to hold yourself to for any given topic. Everything in Fundamentals and Advanced is CORE or PRO — that is why those stages are ordered and gated. The tags do their real work in Mastery, where most material is DEMAND or SPEC and reading it early is wasted effort.

TagStandard
COREKnow cold, without lookup. Non-negotiable
PROKnow well; look up specifics. Expected of a senior
DEMANDKnow it exists. Learn it when a real problem arrives

Getting reviewed

The gap between “I could write a metadata-preserving decorator” and writing one is invisible from the inside, which is the limit of everything on this page — a document cannot tell you how you are doing. Another person reading your code can. How often is your call; these are the places that will.

WhereCostWhat it is good for
Exercism mentoringFreeStart here. You are already on the track daily from Phase 1.1 — request mentoring on a solution instead of just marking it done. Mentors comment on idiom, which is exactly what a solo learner cannot see
Code Review Stack ExchangeFreeWhole working programs. Best for the phase projects. Post the Journal CLI; expect to be told things you did not want to hear
discuss.python.orgFreeDesign questions rather than line-by-line review — “is this the right shape?” Useful from 1.3 onward, once the questions turn architectural
A pull request to a real projectFreeThe best one. A maintainer reviewing your patch against their standards is worth ten self-assessments. Start with a documentation fix — the process matters more than the diff
A colleague, or a paid mentorVariesIf you have access to a working Python engineer this beats everything above on latency alone. Ask for thirty minutes against one file

One thing worth knowing before you post: “any feedback?” reliably gets none. A specific question — “I chose composition over inheritance here, and a Protocol over an ABC; what would you have done?” — gets an answer worth having.

How far to go

The fundamentals are not optional; everything after them is. The order below is a priority order — if you stop, stop at a boundary rather than in the middle of a phase, and know what you are trading away.

If you get throughStatusWhere that leaves you
1.1 onlyStartedYou can write Python. You cannot yet write Python that anyone else should depend on
1.1 → 1.2FloorThe first point worth stopping at. Typed, tested, packaged, CI’d work — the difference between a hobbyist and someone employable
1.1 → 1.3The goalThe point of this whole document. 1.3 is the plateau-breaker — it is why most self-taught developers stall, and why you will not. If you read one phase on this page, make it 1.3

Stage 1

Fundamentals

Complete command of the Python language, applied to real systems — idiomatic, well-tested, properly packaged Python, a real understanding of why the language behaves as it does, and something built that people actually use.

Two hard orderings: 1.1 before 1.3, and 1.3 before 1.4. Everything else is soft, and 1.4 and 1.5 are designed to overlap — build the API while you learn concurrency, then put the concurrency into the API. Each phase has a reading list — complete, in order, nothing missing — and a project list. Read the project list as a specification, not an assignment. It says what a phase needs exercised; it does not say you have to build those particular things. Hand this page to an LLM and ask for projects at the difficulty you want, or build your own idea if it covers the same ground — see How to Practise. Project prompts are short on purpose: scope them yourself. Aim for 20% reading, 20% drills, 60% building — about 1:3, reading to building. A phase is finished when its phase project is finished and you could explain it to someone else.

1.3How Python Really Works

The hinge of everything here

A second pass over 1.1’s ground, at depth. Most self-taught developers never arrive here — which is exactly why they plateau. Don’t rush it. The order below matters more than anywhere else: book for orientation, then the specification, then the stdlib that implements it.

Topics: Names, scope and objects · special methods as protocols · functions as objects and decorators · iterators and generators · context managers · modern class design

Read, in this order

  1. Fluent PythonCh. 1 — The Python Data Model. Read this before the spec, as orientation
  2. Fluent PythonCh. 6 — Object References, Mutability and Recycling. Aliasing, copies, mutable defaults. This is the chapter behind project 1 and the stage exit criterion — do not skip it
  3. Language ReferenceCh. 4 — Execution Model. Names, binding, scope
  4. Language ReferenceCh. 3, §3.1 and §3.3 only — the Data Model. Dense normative prose; expect to reread
  5. Fluent PythonCh. 11, 12, 16 — a Pythonic object, the sequence protocol, operator overloading
  6. Fluent PythonCh. 7, 9 — first-class functions, decorators and closures
  7. Library Ref: functoolsReference, not a chapter. The ones that matter: wraps, partial, lru_cache, singledispatch
  8. Functional Programming HOWTOAll of it
  9. Fluent PythonCh. 17 — iterators and generators. Stop at the classic-coroutines section
  10. Library Ref: itertoolsReference, not a chapter. The recipes at the bottom are the real payload, more than the functions above them
  11. PEP 343The with statement
  12. Fluent PythonCh. 18 — with, match, and else blocks
  13. Library Ref: contextlibReference, not a chapter. @contextmanager, ExitStack, suppress — the rest is rarely needed

Pure stdlib — the last piece of the language

async/await is language syntax and asyncio is stdlib — this is Python, not infrastructure. Last because it needs generators and context managers from 1.3.

1.5Applying Python

The only phase that isn’t Python

This phase is a vehicle, not a subject. Study these shallowly and build with them deeply — the point is exercising Phases 1.1–1.4 under real conditions, not collecting framework knowledge. 1.6Capstones

Three projects

The phase projects were practice. These are the proof — the three things you point at when someone asks what you’ve built. Two concrete options per capstone, so you never have to go looking for an idea. Pick whichever appeals; they’re equivalent in difficulty.

Capstone 1 — A published library

Proves you can design an API other people use, not just code you use yourself.

A
nestdiff

Diff two nested structures (JSON, YAML, TOML configs, API responses) and report exactly which paths were added, removed or changed. Genuinely useful for config drift and API contract checks. Exercises recursion, Protocol, generators for streaming results, and a public API you’ll have to live with.

B
tabular

Render a list of dicts or dataclasses as an aligned terminal table: column selection, alignment, truncation, a totals row, Markdown and CSV export. Exercises __format__, protocols, generics, and the discipline of a small surface area.

Either way it must have: full type hints, mypy --strict clean · pytest plus at least one hypothesis property test · CI across three Python versions · a README with worked examples · a CHANGELOG · published to PyPI. Then maintain it — answer one issue from a stranger.

Capstone 2 — A substantial CLI application

Proves you can structure a real program, not a script that grew.

A
Ledger

A personal finance tracker. Import bank CSV exports (several formats), categorize transactions with user-defined rules, store in SQLite, report by month and category, export results. Exercises file parsing, data modelling, SQL, argparse subcommands, and config files.

B
A static site generator

Markdown with front matter → HTML through templates, incremental rebuild (only what changed), a local dev server, and a link checker. Exercises pathlib, generator pipelines, hashing for change detection, and concurrency for the rebuild.

Either way it must have: subcommands · a config file and env-var overrides · structured logging · a --dry-run for anything destructive · proper package layout, installable and runnable as a command · a test suite you’d trust before a refactor.

Capstone 3 — A backend service

Proves you can build something with users, state, and work happening in the background. This is the one a hiring manager will look at.

A
Read-later service

Save a URL through the API; a background worker fetches the title, description and reading time; tag, full-text search, mark as read. Per-user accounts. Exercises FastAPI, background tasks, httpx, full-text search, auth, and async.

B
RSS aggregator

Subscribe to feeds, poll them on a schedule, deduplicate entries, track unread counts per user, OPML import and export. Exercises scheduled async work, deduplication logic, pagination, and auth.

Either way it must have: authentication and per-user data isolation · a database with migrations · background work that survives a restart — which means a job row in the database, claimed and retried, not FastAPI’s BackgroundTasks, which dies with the process · cursor pagination and a consistent error format · OpenAPI docs · integration tests against a real test database.

Deployment is deliberately not a requirement here. Docker and hosting are outside this roadmap — see What’s Not Here. If you want a public URL, the shortest honest path is a managed Postgres plus one container on any PaaS, and that is a weekend of its own, not part of the capstone.

Exit criteria

Not a test to pass — a description of what the far side of this stage looks like. Anything here you cannot do is a gap that will show later.

The language

  • Predict output involving aliasing, mutation, closures and default arguments — without running it
  • Explain the __hash__/__eq__ contract and what breaks when it’s violated
  • Write a decorator that preserves metadata and works bare or parameterized
  • Explain what super() does in terms of the MRO
  • Reach for a generator instead of a list, by instinct
  • Read any traceback and go straight to the cause
  • Choose correctly between threads, processes and asyncio — and justify it in one sentence

Craft

  • Every project: typed, linted, tested, CI’d — without being told
  • Refactor confidently because the test suite has your back
  • Published a package to PyPI
  • A stranger can clone any repo of yours and run it in two minutes

Applied

  • Build a tested, typed API from empty directory to running service in an afternoon
  • Design a schema, write the migration, and know why your query is slow
  • Every outbound call you write has a timeout and a retry policy, unprompted
The real test

Hand yourself an unfamiliar intermediate Python file — a module from Lib/, say — and you can read it start to finish and explain what every line does and why it was written that way.

Stage 2

Advanced

Finish the Python language. Not “know more Python” — finish it. By the end you can read the standard library’s own source and explain why it was written that way, and the language stops having corners you avoid.

PhaseName
2.1The Language, Completely

Order: 2.1 first, then as you like. Phase 2.3 can be pulled forward to any point after 2.1. The ratio shifts here: closer to 40% reading, 60% building, because the material is denser and the projects are smaller.

Before you start — and whether to start

This stage is optional, and you should feel no pressure to reach it. Plenty of excellent, senior, well-paid Python engineers never read any of it. If the fundamentals are solid and you are building things you are proud of, you have already got what this document is for.

Do domain work first. Stage 1 is enough to be hired on, and everything in Stage 2 lands harder once you have production experience under it — you will have met the problems descriptors and profiling and hexagonal layers actually solve, instead of taking it on faith that they are problems. The strongest version of this path is Stage 1, then a year of real backend, data or platform work, then Stage 2 in the evenings. Going straight from 1.6 to 2.1 is the weaker option, and the one that risks two years of study with nothing shipped for anyone.

Whenever you do start, it reads badly without the groundwork. You should already be able to:

  • Predict output involving aliasing, mutation, closures and default arguments — without running it
  • Explain the __hash__/__eq__ contract and what breaks when it’s violated
  • Write a decorator that preserves metadata and works bare or parameterized
  • Explain what super() does in terms of the MRO
  • Choose correctly between threads, processes and asyncio — and justify it in one sentence
  • Ship code that is typed, linted, tested and CI’d without being told to
  • Have published at least one package to PyPI

If any of those is shaky, go back and fix it first. Everything here compounds on them.

2.4Capstones

Pick two of four

Pick two of the four. Two concrete options under each, so you never have to go looking for an idea. The bar is higher than the fundamentals: these are projects whose source is worth reading, not just whose output works.

Capstone 1 — A library people depend on

Proves you can design something others build on, and support it afterwards.

A
A resilience toolkit

Retries with backoff and jitter, circuit breaker, and timeout, all composable, usable as both decorator and context manager, with sync and async variants from one implementation. Exercises decorators, context managers, contextvars, and async design.

B
A typed configuration library

Layered sources (defaults → file → env → CLI), validation at startup, typed access, and errors that name the exact key and which source set it wrong. Exercises descriptors, generics, and Protocol.

Either way: semantic versioning with a real deprecation policy · tested against three Python versions · 100% typed, mypy --strict · documented with runnable examples · published, and at least one external issue or PR handled.

Capstone 2 — A framework-grade abstraction

Proves you can build the kind of machinery that makes other people’s code shorter.

A
A plugin framework

Entry-point discovery, lifecycle hooks, dependency ordering between plugins, and hook signatures type-checked at registration rather than at call time. Exercises __init_subclass__, inspect, the import system, and ParamSpec.

B
A declarative validation library

Schemas defined as classes, fields as descriptors, nested models, coercion rules, and errors that report the exact path to the bad value. Exercises descriptors, __set_name__, generics, and error design.

Either way: the declarative surface must be genuinely small — if using it is as verbose as not using it, the abstraction failed · a written design document explaining why you chose descriptors over metaclasses, or vice versa · property-based tests · benchmarks showing the abstraction’s overhead.

Capstone 3 — A developer tool

Proves you can work on code as data — the skill behind every linter, formatter and framework.

A
A custom linter

AST-based rules enforcing your own conventions, a plugin interface for new rules, autofix for the mechanical ones, and pre-commit integration. Exercises ast, visitor patterns, and plugin architecture.

B
A test-data factory

Reads your dataclasses and models through inspect and get_type_hints, generates valid instances for tests, handles nesting and constraints, ships as a pytest plugin. Exercises runtime type introspection and plugin APIs.

Either way: runs over a real codebase — ideally one of your own fundamentals projects — and finds something true · zero false positives on that codebase, or a documented reason why · installable and usable by someone who didn’t write it.

Capstone 4 — A performance rewrite

Proves you optimize from measurement rather than instinct.

A
Speed up a real open-source library

Pick one you actually use, profile it honestly, find a genuine hotspot, and submit the PR with benchmarks. The hardest option, and the most valuable if it lands.

B
Optimize your own service under load

Take a fundamentals capstone, put it under realistic traffic, profile with py-spy, fix the top three hotspots, and halve peak memory.

Either way: a reproducible benchmark harness committed alongside the code · flame graphs before and after · an honest account of what you tried that didn’t work — that section is the one that proves you measured rather than guessed · no change merged without a number attached.

Exit criteria

  • Read the source of functools, contextlib and dataclasses and explain why each design choice was made — the real test. If you can do this, you have finished the Python language
  • Derive the attribute lookup order from the data vs non-data descriptor distinction, from memory
  • Explain why list[Dog] is not a list[Animal], and design around it
  • Read a framework’s metaclass-driven source and follow it without getting lost — and choose not to write one yourself
  • Debug a deadlock and a race condition in unfamiliar code
  • Profile a real system and prove every speedup with numbers
  • Structure a package so “where does this code go?” has an obvious answer
  • Design a public API and ship a deprecation without breaking anyone

Stage 3

Mastery

A reference, not a curriculum. No phases, no capstones, nothing to finish — because the material doesn’t work that way. You read the import system when imports break. You read gc and tracemalloc when something leaks. You read dis when a benchmark makes no sense. Read any of it speculatively and none of it retains.

✓Who actually needs this

  • Maintainers of widely-used libraries
  • Authors of native extensions
  • Engineers doing performance work at the interpreter boundary
  • CPython contributors

!Who doesn’t

  • Almost everyone else
  • Plenty of excellent, senior, well-paid Python engineers never open any of it
  • Nothing is wrong with that
  • Treat this as something you grep when a problem arrives, not a gap in your education

Part 1 — The trigger index

The reactive majority of this material. Find your symptom, read the two or three things next to it, fix the problem, move on.

When this happensReadThen
Imports fail in a way that makes no sense — circular imports, a module shadowed, something resolving to the wrong file Language Reference ch. 5 — finders, loaders, sys.meta_path · importlib Trace the failure through the finder/loader machinery and write down the resolution. You’ll hit it again
A long-running process keeps growing gc — cycles and generational collection · tracemalloc · memray for the hard cases · weakref Find the cycle or the cache that never evicts. sys.getsizeof will lie to you; don’t trust it alone
Two equivalent functions benchmark differently dis · PEP 659 — the specializing adaptive interpreter Read the bytecode of both and explain the difference from it. If you can’t, the difference is probably elsewhere
You need to analyze or rewrite source programmatically — a linter, codemod, or custom check ast · inspect Work on the AST, never on text. Every regex-based refactor tool eventually corrupts something
You need to know what the interpreter is doing live — a debugger, profiler, or coverage tool sys.monitoring (PEP 669) · sys.settrace / setprofile · PEP 768 This is how every Python debugger works. Useful the day you need to build one
Pure Python is genuinely too slow — and you have the profile to prove it Extending and Embedding · PyO3 user guide for Rust · ctypes / cffi for existing libraries See Track A below. Don’t start here without a profile — “it felt slow” is not a reason to leave Python
Objects use more memory than they should __slots__ · interning behaviour · sys.getsizeof and its limits Measure three representations of the same data before choosing one
A C extension misbehaves under free threading Free-threading HOWTO · C API support for free threading Increasingly common as 3.13+ free-threaded builds spread

Part 2 — The two deliberate tracks

Unlike everything above, these two are chosen projects with a real sequence. You don’t stumble into them — you decide to do them.

Track A — Write a native extension

For when profiling has proven a hotspot and Python genuinely can’t close the gap.

Track B — Contribute to CPython

For when you want to work on the language itself.

  3. Fix a documentation issueAnd get it merged. A real PR through the real process, with low stakes

What mastery actually looks like

Not a checklist to complete — a description of someone who got here. You’ll recognize when it’s true.

  • Diagnose a memory leak in a long-running production process
  • Read dis output and explain a performance difference from it
  • Trace an import failure through the finder/loader machinery
  • Ship a native extension that measurably beats pure Python
  • Merge a contribution into CPython or a major library
  • Maintain a library others depend on, with a real deprecation policy
  • Teach this material to someone else and have it land
The one that counts

The last item is the real test. Everything above can be faked with enough reading; that one can’t.

Practice

How to Practise

This page names what to read and what to build. It does not contain the practice in between — and it should not. There is far more of it than any document could hold, and the right amount differs for every reader. Generate it instead.

Exercism is the ready-made option and it has human mentoring attached, which nothing below replaces. For practice aimed at exactly what you just read, an LLM will produce it on demand. The prompts below are the ones worth keeping. Each is written to be pasted together with this page, or with just the phase you are in — give it the whole document where you can, because then it can see what earlier phases built and what later ones depend on, which is the part you would otherwise have to explain.

Start the session once, then reuse it

Set the standing rules at the top of a conversation and every prompt below inherits them. This is what stops a model handing you answers you have not earned.

I am working through a Python roadmap. Here it is:

<paste this page, or the phase you are in>

I am on Phase <X>. I have covered everything up to
<the last reading item you finished>, and nothing after it.

Rules for this whole conversation:
- Never give me a solution to something I have not attempted first.
- Never use a feature or module from a later phase in an example.
- When you correct me, point at the official documentation rather
  than asserting it yourself.
- If I ask for an answer too early, ask me what I have already tried
  instead of answering.

Acknowledge these and wait. Do not start teaching yet.

Telling it what you have not covered matters as much as what you have. Without that line you will get itertools in week two, and a model cannot tell that this is a problem.

Which prompt, when

Where you areUse
You have finished a reading item1
The topic is one where intuition is often wrong — names, mutability, scope, concurrency2
You think you have understood something and want to find out3
A listed project does not suit you, or is the wrong size4
You are about to start building5
You are stuck on a bug6
You have finished something and want it read7
You are starting a phase and the last one has gone cold8

1 — Drill a topic you just read

After any reading item, before you move to the next one.

I am working through a Python roadmap one topic at a time.

I have just read: <the exact chapters or doc pages>
I have not yet covered: <the next few items on the list>

Give me 8 practice problems on exactly that material, easiest first.

- Use only language features and standard-library modules from what
  I have already covered. If a problem needs something later, drop it.
- Give me the problems only. No solutions, and no code in your reply.
- For each one, name the section of the official docs it maps to,
  so I can check myself.
- Make at least two of them cases where the obvious approach is
  subtly wrong.
- When I send you my attempt, tell me what is incorrect and what is
  unidiomatic — but do not rewrite it for me.

2 — Predict, then check

The highest-value technique on this page. Phase 1.3 uses it explicitly; it works for any topic where your intuition might be wrong.

Give me 12 short Python snippets covering <topic>.

- Each should print something, or raise.
- Choose cases where a reasonable person predicts the wrong answer.
- Number them. Give me no output and no explanation yet.

I will write my prediction for every one before running them. Then I
will send you my predictions, and you tell me which are wrong and why,
pointing at the docs rather than just asserting it.

Write the predictions down before you run anything. The value is entirely in committing to an answer while you can still be wrong about it — reading the output first teaches almost nothing.

3 — Explain it back and find the holes

Recalling something badly and then correcting it holds far better than rereading it. Write the explanation before you look anything up.

I have just finished <topic>. Here is my explanation of it,
written from memory without looking anything up:

<your explanation>

Find what is wrong, what is missing, and what I have stated more
confidently than I should have.

- Quote the documentation for each correction.
- Do not fill the gaps for me — name the section I should go
  and read instead.
- Rank what I got wrong by how much it will cost me later.

4 — Projects at your own difficulty

The project lists are set at one difficulty, which will be wrong for somebody. Read them as a specification of what a phase needs exercised, then get your own.

<paste this page, or just the phase you are in>

I am on Phase 1.3. Propose 6 projects for it instead of the
listed ones.

- They must exercise the same things the listed projects exercise,
  and nothing that needs a later phase.
- Difficulty: <harder / about the same / smaller, and more of them>
- Where a listed project continues earlier work, keep that — and
  tell me which earlier project it builds on.
- If I describe something I actually want to build, tell me honestly
  which of the phase's topics it does not cover.
- List them and stop. Do not pick for me.

5 — Scope something before you start it

Project prompts here are one line on purpose. This is how you turn one into a week of work without it quietly becoming three.

I am about to build: <the project, in one or two sentences>
I have covered: <phases or topics>

Help me scope it, not build it.

- What is the smallest version that still exercises the point?
- What should I deliberately leave out of the first version?
- Which parts will take far longer than I expect, and why?
- What decisions should I make now because they are expensive to
  change later?

No code, and no implementation plan. Questions and trade-offs only.

6 — Get unstuck without getting the answer

The failure mode of having a model to hand is that debugging stops teaching you anything. This keeps the loop intact.

Here is code that is not doing what I expect, and what I expected:

<code, and the behaviour>

Do not tell me the cause and do not fix it.

Ask me the questions you would ask to narrow it down, one at a time.
If I am looking in the wrong place entirely, say so without saying
where the right place is. Point me at the documentation that covers
the behaviour I have misunderstood.

7 — Have your code read back to you

Useful between human reviews, and no substitute for one — see Getting reviewed.

Review this as a senior Python engineer would in a pull request.

<code>

- Be specific and be blunt. Name what you would block the PR on.
- Separate correctness bugs from style from design.
- Where you say something is unidiomatic, show the idiom by name
  and link the docs — do not rewrite my code.
- If parts of it are genuinely fine, say so briefly rather than
  inventing criticism.

8 — Come back to a phase that has gone cold

The start of a reading list fades while you work through the end of it. Run this at the top of each new phase; it takes twenty minutes and finds what actually slipped.

I am starting Phase <X>. I last worked on Phase <Y>
a while ago.

Ask me 10 questions on <Y>'s material, one at a time, waiting
for my answer before the next.

- Mix straight recall with "what happens if" cases.
- Do not tell me the answer until I have given mine.
- At the end, tell me which parts of <Y> I should reread before
  continuing, in priority order — and which I clearly still have.

Where this goes wrong

  • The answer is always one question away. Prompt 2 only works because you commit to a prediction before you check it. A model will hand you the output the moment you ask, and the exercise is worth nothing after that
  • Generated material is wrong often enough to matter. The docs are the authority; a model is not. Anything surprising is worth checking against the page it came from — which is the habit the rest of this roadmap is built on anyway
  • A model will agree with you. Agreement is not feedback, and it is not a substitute for a person reading your code
  • Generated practice is not a syllabus. It is good at drilling a topic you name and poor at telling you which topic matters next. That ordering is what this page is for — do not hand it over

The short version

Two books and one website carry the fundamentals. Three more books carry Advanced — and one of those you already own.

Why isn’t it one book?

No such book exists, and the reason is structural rather than a gap in the market.

  1. The language is documented better than any book covers itThe Tutorial and Language Reference are free, authoritative, and track the current version. A book is a snapshot that starts aging the day it ships.
  2. Tooling turns over every few yearsuv and ruff are recent and have already displaced older tools. Any book naming a toolchain is wrong within two editions.
  3. Frameworks move faster stillFastAPI’s own docs are better than any book about FastAPI, and they’re current.
  4. The closest thing that existsFluent Python — it covers roughly Phases 1.1, 1.3 and 1.4. It does not cover testing, packaging or tooling, and it predates 3.12–3.14.

  5. The C API and metaclass authoring before Advanced is completeInteresting, unretained, and not what anyone will ask you to do.
